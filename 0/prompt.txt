# RecallDesk — Build Feature 3: Decision & Task Memory

You are working on my existing project, RecallDesk, a local-first desktop application built with Electron, React, TypeScript, and electron-vite.

## Context

RecallDesk already has:
- Local folder indexing for text files, Markdown, and source code.
- Semantic search using `@huggingface/transformers` and `Xenova/all-MiniLM-L6-v2`.
- Keyword-based search combined with semantic search.
- Search results with source file paths and relevant text excerpts.
- A local AI integration using Ollama, intended to answer questions using indexed content and provide source references.
- A packaged macOS `.dmg` build.

The project uses:
- `src/main/index.ts` — Electron main process, indexing, search, persistence, and IPC handlers.
- `src/preload/index.ts` — secure API exposed through `contextBridge`.
- `src/renderer/src/App.tsx` — React UI.
- `src/renderer/src/vite-env.d.ts` — renderer API types.
- `app.getPath('userData')` — local application data storage.

Inspect the actual repository before changing anything. Do not assume the current files exactly match this description.

## Goal

Build Feature 3: Decision & Task Memory.

RecallDesk should help users discover unfinished work and important decisions from their indexed local documents, project notes, Markdown files, and source code.

Examples:
- Task: “Finish the authentication flow before Friday.”
- Task: “Add retry handling to the API client.”
- Decision: “Use PostgreSQL instead of MongoDB for the production database.”
- Decision: “Keep embeddings and document indexing local.”
- Task: “Fix the failing integration tests.”

These are examples, not fixed rules. Extract items only when the indexed content provides reasonable evidence.

## Critical requirements

1. Local-first and privacy-first.
2. Never automatically mark an extracted item as a confirmed task or decision.
3. Every suggestion must include its source file and supporting excerpt.
4. Let users confirm, edit, dismiss, complete, and reopen items.
5. Avoid duplicate suggestions when extraction runs repeatedly.
6. Do not invent deadlines, priorities, decisions, or commitments.
7. Preserve all existing indexing, semantic search, keyword search, and local AI functionality.
8. Do not send indexed files or user content to external APIs.
9. Do not introduce a cloud database, analytics, telemetry, or unnecessary dependencies.
10. Keep the feature usable when Ollama or the embedding model is unavailable.

- `relativePath`: relative path when available.
- `sourceExcerpt`: text supporting the suggestion.
- `status`: `suggested`, `open`, `completed`, or `dismissed`.
- `confidence`: optional confidence score, with a documented interpretation.
- `dueDate`: optional; only set when explicitly supported by the source or entered by the user.
- `createdAt`: timestamp.
- `updatedAt`: timestamp.
- `contentHash` or another stable deduplication key.

Adjust the model if the existing architecture suggests a better approach.

## Phase 3 — Extract candidate tasks and decisions

Requirements:

- Inspect the actual Ollama request and response format before implementing extraction.

- Use a strict JSON output schema and validate model output before saving anything.
- Handle malformed JSON, empty responses, timeouts, and Ollama being unavailable.
- Never treat arbitrary code comments, TODO strings, hypothetical examples, or quoted instructions as confirmed user commitments without appropriate context.
- Distinguish a real decision from a suggestion, alternative, unresolved discussion, or hypothetical statement.
- Include a source excerpt that can be verified against the original indexed chunk.
- Avoid extracting the same item repeatedly.
- Preserve the original source path and enough context to let the user verify the claim.

Do not automatically extract the entire index on every application launch. Provide an explicit action such as “Find tasks and decisions” and show progress while processing.

# RecallDesk — Build Universal Project Intelligence

## Product vision

Transform RecallDesk from a local file-search and task-tracking application into a universal, privacy-first Project Intelligence assistant.

RecallDesk must eventually work with more than source code or folders. It should help users understand their work across documents, screenshots, images, notes, code, and other supported sources.

The central question is:

"What am I working on, what matters, and what should I do next?"

The application should analyze user-selected context, extract evidence-backed findings, suggest useful next actions, and allow users to manage those actions through the existing Tasks & Decisions system.

## 1. Inspect the existing application first

RecallDesk currently uses Electron, React, TypeScript, electron-vite, local file indexing, semantic search through Hugging Face Transformers, and a local Ollama integration.

Relevant files include:

- `src/main/index.ts`
- `src/preload/index.ts`
- `src/renderer/src/App.tsx`
- `src/renderer/src/vite-env.d.ts`
- `src/main/memory/`
- `src/renderer/src/styles.css`
- `package.json`

Inspect the actual repository, existing interfaces, current file support, IPC handlers, local AI integration, and test setup before making changes.

The current Tasks & Decisions feature already supports persistent memory records and a review workflow. Reuse and extend it rather than creating a second task system.

Do not assume that every file format or image capability already exists.

## 2. Build a universal source-selection workflow

Add a Project Intelligence workspace where users can select what they want to analyze.

Support these source types according to actual implementation capability:

- Individual files.
- Multiple selected files.
- Entire folders and projects.
- Previously indexed content.
- PDFs and text documents.
- Markdown and plain-text notes.
- Screenshots and other images.
- Other formats through future source adapters.

Users should be able to add multiple sources to one analysis.

Reuse the existing secure folder picker, file-opening mechanisms, and indexing pipeline where appropriate. Add a dedicated file picker for individual files and multiple files.

Allow analysis of selected files without requiring the user to index an entire folder first.

Display the selected sources before starting analysis, including their names, types, and any unsupported-format warnings.

Never silently ignore unsupported files.

For large folders, provide progress information and sensible limits. Respect existing excluded directories, file-size limits, and user-selected scope.

## 3. Support different analysis goals

Provide built-in analysis modes:

### Project overview
Explain what the selected material contains, its purpose, major components, and current state.

### What should I do next?
Identify actionable work based on the available evidence and the user's stated goal.

### Extract tasks
Find explicit tasks, TODOs, deadlines, commitments, acceptance criteria, and action items in documents and notes.

### Decisions and open questions
Identify documented decisions, their rationale, alternatives, unresolved questions, and decisions that may need confirmation.

### Find potential issues
Identify evidence-backed concerns, inconsistencies, incomplete requirements, and potential risks.

Do not claim that a code defect exists unless the available evidence supports that conclusion. Distinguish confirmed failures, explicit TODOs, inferred risks, and suggestions.

### Analyze screenshots and images
Interpret visible text, interfaces, diagrams, error messages, whiteboards, and handwritten notes when the selected local model supports the required vision capability.

### Custom instructions
Let users describe a specific analysis goal in their own words.

Allow users to select a goal and optionally provide additional instructions before starting analysis.

## 4. Design a common source-adapter architecture

Create a maintainable architecture that separates source ingestion from analysis.

A source adapter should provide, where supported:

- Source ID.
- Original file path.
- Display name.
- Source type and MIME type.
- Extracted text or other supported content.
- Source metadata.
- Evidence locations, such as page numbers, line ranges, or image regions when available.
- Extraction status and errors.

Use appropriate parsers for supported document formats.

For screenshots and images, use a local vision-capable model or OCR pipeline only when available and compatible. Do not assume a text-only Ollama model can analyze images.

Keep image bytes, document content, and other sensitive data on the local machine.

Design adapters so future formats can be added without rewriting the task-management system.

## 5. Build the analysis pipeline

The workflow should be:

1. Validate the user's selected sources.
2. Extract text or other supported representations.
3. Preserve source metadata and evidence locations.
4. Prepare relevant context within the configured local model's limits.
5. Run the selected analysis goal through the local AI integration.
6. Validate the model's structured output.
7. Verify that source excerpts correspond to actual extracted content.
8. Deduplicate findings.
9. Present results for user review.
10. Allow approved tasks and decisions to be saved into persistent memory.

Use batching, progress reporting, cancellation, and graceful error handling where appropriate.

For large folders, analyze manageable batches and provide an overall summary without exceeding model context limits.

Do not send files to external AI services. Do not add telemetry or cloud dependencies.

If a local model is unavailable or lacks the required capability, explain the limitation and offer a supported alternative. For example, text extraction may still work when image understanding is unavailable.

Do not pretend that an image was visually analyzed if only its filename or metadata was read.

## 6. Use structured, evidence-backed findings

Define a typed finding model that can represent:

- Tasks.
- Decisions.
- Requirements.
- Open questions.
- Potential issues.
- Recommendations.
- Project summaries.

Each finding should include, when applicable:

- Unique ID.
- Finding type.
- Title.
- Description.
- Reason or rationale.
- Source references.
- Supporting excerpts or evidence.
- Confidence or evidence classification.
- Review status.
- Creation and update timestamps.

Use explicit evidence classifications such as:

- Explicitly stated.
- Directly observed.
- Inferred.
- Suggested.

Do not treat confidence scores as guarantees of correctness.

Keep evidence references linked to the original file and, when available, page number, line range, or image region.

For image findings, include an explanation of the visible evidence and distinguish OCR text from visual interpretation.

If a claim cannot be traced to the supplied material, label it as an inference or omit it.

## 7. Integrate with Tasks & Decisions

Reuse the existing persistent memory store and CRUD operations.

Users should be able to:

- Accept a suggested task.
- Edit a task before accepting it.
- Dismiss an irrelevant finding.
- Mark a confirmed task as completed.
- Reopen a completed task.
- Save a documented decision.
- Edit or archive a decision.
- Open the original source.
- Review the evidence behind a finding.

Never automatically convert every AI recommendation into a confirmed task or decision.

Preserve the distinction between discovered suggestions, user-approved tasks, documented decisions, and AI-generated recommendations.

Avoid duplicates across repeated analyses, but do not merge unrelated tasks merely because their wording is similar.

## 8. Design the user interface

Add a Project Intelligence workspace that matches RecallDesk's existing visual design.

It should include:

- Source selection.
- A list of selected sources.
- Analysis mode selection.
- Optional custom instructions.
- Start analysis and cancel controls.
- Progress and error states.
- A project overview.
- Categorized findings.
- Source evidence.
- Actions to accept, edit, dismiss, or open a source.
- A clear way to send accepted tasks and decisions into the existing Tasks & Decisions views.

Keep Search Memory, existing indexing, embeddings, and current AI question-answering functionality intact.

Avoid unnecessary UI libraries and avoid overwhelming the user with configuration options.

## 9. Privacy and security

- Keep processing local.
- Use Electron's existing secure IPC patterns.
- Validate all renderer-provided file paths and operations in the main process.
- Do not expose unrestricted filesystem APIs to the renderer.
- Avoid reading outside the user's selected scope without explicit permission.
- Respect symlinks and directory traversal protections.
- Do not execute code found in analyzed files.
- Do not modify project files as a side effect of analysis.
- Do not automatically create, delete, or edit source files.
- Store analysis results and memory records using safe local persistence.
- Explain what is unsupported or failed rather than silently producing incomplete results.

## 10. Implementation strategy

Implement this incrementally.

Phase A:
Create the Project Intelligence workspace and dedicated source-selection workflow. Support individual files, multiple files, folders, and existing indexed content.

Phase B:
Implement reliable text extraction for currently supported formats and add appropriate document parsers for the next formats.

Phase C:
Connect the analysis goals to the existing local AI integration and return structured findings with source evidence.

Phase D:
Add screenshot and image analysis through an appropriate local OCR or vision-capable pipeline. Verify model compatibility before implementation.

Phase E:
Integrate findings with Tasks & Decisions, including review, approval, deduplication, and persistence.

Phase F:
Add tests for source adapters, unsupported formats, extraction errors, malformed AI output, evidence validation, duplicate handling, cancellation, persistence, and IPC security.

Do not attempt to implement every future format in one step. Build a working end-to-end path first and expand it through source adapters.

## 11. Verification

Run the existing type checks, tests, and production build.

Test manually with:
- A code project containing explicit TODOs.
- A Markdown project plan.
- A document containing a list of action items.
- A screenshot containing readable text.
- A mixed collection of files.
- An unsupported file format.
- An unavailable local model.
- A repeated analysis of the same source.

Document which formats and model capabilities actually work. Do not claim image understanding, PDF support, or other capabilities until they have been implemented and verified.

Start by inspecting the repository, then implement Phase A as a complete working feature. Continue into Phase B only as far as can be done safely without breaking the existing app. Report modified files, commands run, test results, and known limitations.
